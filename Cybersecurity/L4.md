# Email system and security challenges

## Email spoofing
It consists in sending an email with a fake sender in order to steal confidential data or deliver malware to the victim. In general, this kind of attack doesn't directly break a system: its success depends on the victim's trust.<br>
A first sign of a spoofing attack is that envelope and header don't coincide:
- EG.
    - Delivered-To: leonardo.querzoni@uniroma1.it (header filled from the RCPT TO of the envelope, the real recipient)
    - To: polizia-cr@info.it (visible header)

Another one is the presence of a fake thread, used to simulate a previous discussion that never happened:
- EG.
    - In-Reply-To or References

Another one is the fact that the display name and the actual address are unrelated:
- EG.
    - From: Polizia criminale <alessandro.lazzaro@uniroma1.it>

Finally, the most dangerous inconsistency: the From and Reply-To fields do not match. You see a trusted address in the From, but if you reply, the answer goes to the attacker's address.

Most of these threats stem from the lack of adequate security guarantees in the standard email architecture and its protocols. In particular:
- No sender authentication means no way to trace the origin of an email
- No end-to-end encryption means no way to enforce content confidentiality

To address these problems, email authentication protocols were introduced.

## SPF (Sender Policy Framework)
SPF solves the following problem: anyone can write an address of any domain in the MAIL FROM command (envelope). What SPF does is let the domain owner define a set of servers authorized to send emails that contain that domain in the MAIL FROM.<br>
This mechanism works with DNS.<br>
However, SPF protects only the MAIL FROM, not the From and Sender fields (header), so these two can still be falsified.

Another characteristic: the server that accepts the mail copies the content of MAIL FROM into an additional header field, Return-Path. In the same way, Delivered-To (header) takes its value from RCPT TO (envelope).

### How it works?
When a server receives an email:
1. it reads the domain in MAIL FROM
2. it sends a query to DNS to get the SPF record associated with the domain
3. it checks if the IP of the sending server, the one that opened the SMTP connection, falls within the authorized ones.
    - Pass: check ok
    - Fail: the receiving server can reject the mail or mark it as spam.

### How to set SPF?
EX.
Bob has the domain example.net and the address bob@example.net, but it happens that:
1. a spammer sends hundreds of emails with MAIL FROM = bob@example.net
2. many of them get rejected
3. the bounce errors go to Bob's mailbox

- this phenomenon is called backscatter

Now Bob wants to allow the sending of his emails only from a few machines: his mail servers, his own machine and Gmail servers. So he publishes a TXT record in DNS as follows:
- example.net  TXT  "v=spf1 mx a:pluto.example.net include:aspmx.googlemail.com -all"
    - mx: the mail servers of the domain are authorized
    - a:pluto.example.net: the machine pluto is authorized
    - include:aspmx.googlemail.com: all the servers authorized by Google are authorized
    - -all: every other server is not authorized

The spammer sends from his server, with IP 66.66.66.66 and MAIL FROM: bob@example.net. The recipient server:
- sees that the MAIL FROM belongs to example.net;

- asks DNS for the SPF record of example.net;

- checks if 66.66.66.66 is among those authorized. It is not an MX server of Bob, it is not pluto, and it does not belong to Google: it falls under -all;

- result fail, and it rejects the email immediately, during the SMTP session.

### Limits of SPF
1. SPF authorizes only the servers listed in the record. If a legitimate email is delivered by a server not on the list (forwarding, mailing lists, third-party services not included), it fails the check and risks being discarded or ending up in the spam folder.

2. There is a problem with records that are too large: DNS responses travel over UDP in packets of at most 512 bytes, so if the record doesn't fit inside one there are problems. So the includes should be used moderately (there is also a limit of 10 DNS lookups per check).

3. SPF checks who is delivering the email, not what is inside it. If someone intercepts the email and alters the text, a link, or an attachment, and then delivers it from an authorized server, the SPF check still passes.

4. An attacker registers his own domain and publishes an SPF record with his IP:
    - attacker.com  TXT  "v=spf1 ip4:66.66.66.66 -all"

    then he sends with MAIL FROM: x@attacker.com (envelope) and From: info@realbank.com (header). SPF checks only the MAIL FROM domain, so it passes, while the user sees a fake From address.

## DKIM (DomainKeys Identified Mail)
SPF, very shortly, checks only which server the email comes from, but header and body are ignored.<br>
DKIM implements a solution based on signatures: the sender domain applies a cryptographic signature to the mail.

What it guarantees:
- integrity: the email content isn't modified during transit
- domain authentication: the email was really signed by the declared domain
- non-repudiation: the sender domain can't deny having sent the message

Two types of keys are used:
- private key: only the sender domain knows it and uses it to sign the message.
- public key: it is published by the same domain in DNS; anyone can read it and use it to verify the signature.

Last thing: DKIM works only with headers and body, the ENVELOPE is ignored.

### How it works?

1. Bob sends an email from bob@example.net
    - the server of the domain (example.net) takes the body and some header fields and applies a hash to them; the result is a fingerprint
    - the fingerprint is signed with the private key
    - the server adds the signature to the mail as a new header, **DKIM-Signature**, together with other information needed to verify it; the most important are:
        - d: the domain that signs (example.net)
        - s: the selector
        - h: the headers used to build the signature

2. The domain publishes the public key in its DNS, in a record with a fixed name composed of selector + _domainkey + domain:
    - the record's p field contains the key

3. When the email arrives, the receiving server:
- reads the DKIM-Signature and finds d=example.net and s=mail2024;

- queries DNS for mail2024._domainkey.example.net and retrieves the public key;

- recalculates the hash of the body and of the headers specified in h=;

- uses the public key to verify that the signature matches that hash.
    - Pass: the email hasn't been changed
    - Fail: DKIM only reports the result, what to do is decided by DMARC

A domain can have multiple active keys at the same time. The selector indicates which key was used: it is the name preceding ._domainkey.

EX.
mail2024._domainkey.example.net<br>
agenzia._domainkey.example.net


## DMARC
SPF and DKIM don't apply any kind of check on the From header, and in general when one of these two protocols fails, the decision on what to do is taken locally by each server.<br>
What DMARC provides is a link between SPF/DKIM and the From header, through alignment, and it gives the domain owner the possibility to define what to do with failing emails.

### How it works?
1. The domain owner (EX. example.net) publishes a TXT record in DNS:
    - _dmarc.example.net
        - p field contains the policy, that is what to do with failing emails (none, quarantine, reject)
        - pct: percentage of failing emails to which the policy is applied
        - rua / ruf: addresses where aggregate / forensic reports are sent

2. An email arrives. The recipient server performs these operations in order:
    - The server takes the domain from the **From header** and reads the _dmarc. record of that domain. This is the major difference compared to SPF and DKIM: DMARC starts from the From header visible to the end user.

    - It checks 3 things:
        - Is the DKIM signature valid?
        - Does the email originate from an IP authorized by the SPF record?
        - Are the domains "aligned"?

    - Alignment is the core of DMARC. It means that the domain verified by SPF or DKIM must match the domain in the From header.
        - SPF alignment: the domain in the From header (RFC 5322) must match the domain in the Return-Path header / MAIL FROM envelope sender (RFC 5321), which is the domain verified by SPF;

        - DKIM alignment: the domain in the From header must match the d= domain in the DKIM signature.

    - DMARC passes if at least one between SPF and DKIM passes and is aligned; otherwise it fails and the policy is applied.

3. After deciding what to do with the email, the recipient server reports the outcome to the owner of the domain found in the From header.

## ARC (Authenticated Received Chain)
DMARC basically has a problem with mailing lists: at a certain point the mail reaches a server (intermediary) that modifies the message and forwards it to a number of addresses. As a result SPF and DKIM fail, and so DMARC fails too, even if the email is legitimate.<br>

The ARC idea: when there are one or more intermediaries, each of them writes a declaration inside the mail (the result of the checks it performed when it received it), signed with its private key. So at the end the mail carries a chain of declarations.

First of all, ARC is not a substitute for DMARC: it is a component that works alongside it and offers the receiver more information on emails where DMARC fails.


### Why ARC works?
There is a header never named till now: **Authentication-Results**.
When a server receives an email, it writes the output of the checks inside it:
```text
Authentication-Results: lista.org;
    spf=pass smtp.mailfrom=alice@example.net;
    dkim=pass header.d=example.net;
    dmarc=pass header.from=example.net
```
But this header doesn't have a signature, so basically anyone can write anything in it, and here comes ARC.<br>
ARC takes this information and makes it reliable.

### How it works?
Every intermediary that implements ARC adds to the mail three headers grouped in a single set. Every set is identified by a progressive number i= (new intermediary = new set i+1).

- headers:
    1. ARC-Authentication-Results (AAR):
        a copy of the Authentication-Results, it contains the result of the checks done by the current intermediary

    2. ARC-Message-Signature (AMS):
        a DKIM-style signature of the message, it includes also the AAR in the calculation but excludes the ARC-Seal

    3. ARC-Seal (AS): another DKIM-style signature, but it uses only the ARC headers (those of the previous sets plus the current AAR and AMS), so it doesn't use body or standard headers. It protects the chain.


Summarizing what an intermediary does:
- Creates the AAR. Copies the contents of its own Authentication-Results into a new ARC-Authentication-Results header and prepends it to the email.

- Calculates the AMS. Signs the message, including the newly created AAR but excluding any ARC-Seal, and prepends the ARC-Message-Signature header to the top.

- Calculates the AS. Signs all ARC headers and prepends the ARC-Seal header to the top.

### ARC limits
ARC says nothing about the trustworthiness of the sender or of the intermediaries. This is the most significant limitation: an ARC signature proves who made the attestation, not that the attestation itself is true. So the receiver uses the chain only if it trusts the intermediaries.

ARC only deals with authentication: whether SPF, DKIM, and DMARC were valid. It does not indicate whether the email is spam, phishing, or contains a malicious attachment. An email with a perfectly valid ARC chain can still be malicious, and an intermediary might even inject bad content itself.

An intermediary can partially or completely strip the ARC headers of previous hops. If it removes only some of them, subsequent seals fail to validate, breaking the chain. If it removes all of them, the email arrives as if ARC had never been used. In both cases, the recipient loses this context, and the email is evaluated solely based on DMARC.

## PGP (Pretty Good Privacy)
SPF, DKIM, DMARC and ARC are managed by the servers and authenticate only the domain, but none of them solves the second problem seen at the beginning: there is no end-to-end encryption, so the content of the email can be read by anyone who intercepts it.<br>
PGP works directly between the users: the sender's client signs and encrypts the email, and only the receiver's client can decrypt it. The servers in the middle see only encrypted data.

What it guarantees:
- authentication and integrity: the message is signed by the sender (a person, not a domain like in DKIM), so the receiver knows who wrote it and that it wasn't modified
- confidentiality: the message is encrypted, so only the receiver can read it

The two services can be used separately or together.

Every user has a pair of keys: the public key is given to the others, the private key is kept secret. In addition, for every message a temporary key is created, the session key.

### How it works?
EX. Alice sends to Bob an email both signed and encrypted.

1. Alice signs the message
    - she computes the hash (SHA-1, 160 bits) of the message
    - she encrypts the hash with her private key (RSA): the result is the signature, which is attached to the message

2. Alice compresses message + signature (ZIP)

3. Alice encrypts
    - she generates a random 128-bit session key, used only for this message
    - she encrypts message + signature with the session key (symmetric encryption)
    - she encrypts the session key with Bob's public key (RSA) and attaches it to the message

    Why two keys? Symmetric encryption is fast, so it is used for the message, which can be long; RSA is slow, so it is used only for the session key, which is short. And since the session key is encrypted with Bob's public key, only Bob can recover it.

4. Bob decrypts
    - he decrypts the session key with his private key
    - with the session key he decrypts message + signature, then decompresses them

5. Bob verifies the signature
    - he decrypts the signature with Alice's public key and obtains the hash computed by Alice
    - he computes the hash of the received message
    - if the two hashes are equal, the message comes from Alice and wasn't modified

Why compress after signing but before encrypting? The signature is computed on the uncompressed message, so Bob can store the message with its signature and verify it later. Moreover compression is not deterministic (different implementations can produce different outputs): if the signature were computed on the compressed message, the verification would require compressing again and could fail on legitimate messages.

### Key ID and key rings
A user can have many key pairs, so Bob must know which of his keys Alice used. Sending the full public key with every message would be inefficient, so PGP uses a Key ID: the least significant 64 bits of the key, which are very likely unique. The message contains Bob's Key ID (to find the key that decrypts the session key) and Alice's Key ID (to find the key that verifies the signature).

The keys are stored in two key rings, indexed by Key ID:
- public-key ring: the public keys of the other users
- private-key ring: the user's own key pairs. The private keys are stored encrypted, with a key obtained from the hash of a passphrase

So, in the previous example, Alice has to type her passphrase to unlock her private key before signing (step 1), and Bob has to do the same before decrypting the session key (step 4). The security of the private keys depends on the security of the passphrase.

### Key management
A problem remains: how can Alice be sure that the public key she uses really belongs to Bob? PGP doesn't use certificate authorities (CA): every user is his own CA and can sign the public keys of the people he knows directly.

In this way a "web of trust" is created:
- a key signed by me is trusted
- I can trust also a key signed by others, if there is a chain of signatures from me to it
    - EX. I signed Alice's key, Alice signed Bob's key, so I can trust Bob's key

The key ring also contains trust indicators (how much I trust each key and its owner), and users can revoke their keys, for example if the private key is stolen. Keys are often signed during key-signing parties, meetings where people verify each other's identity and sign each other's keys.
