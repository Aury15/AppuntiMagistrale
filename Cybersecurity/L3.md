# E-Mail system
The e-mail system is based on a **store-and-forward** model and on **asynchronous** interaction: e-mail servers accept, forward, store and deliver messages, so the sender and the receiver don't need to be online at the same time. <br>
Its architecture has many components, grouped in 3 different parts:
- *Message author*
- *Message handling system (MHS)*
- *Message recipient*

### Message author
**Message User Agent (MUA)** is basically the mail client, where the sender writes the e-mail.
The MUA formats and builds the e-mail, then forwards the message to the MSA (using the Submission protocol, a variant of SMTP).

### Message handling system
**Message Submission Agent (MSA)** receives the message from the MUA and makes sure it meets the standard format. Then it looks at the destination address and asks the DNS for the **MX records** of the recipient's domain, to find the FQDN of the recipient's mail server. At the end it gives the message to the MTA.
- FQDN (Fully Qualified Domain Name) is basically the complete name of a host
- EX: **mx.b.org**
    - mx → name of the machine
    - b → second level domain
    - org → top level domain
- in an e-mail we just write *bob@b.org*: the DNS answers with the MX record (mx.b.org), and from that name we get the IP address of the server.

**Mail Transfer Agent (MTA)** implements both the client and the server parts of the SMTP protocol; its main job is forwarding the message to the next MTA. The chain has at least 2 MTAs (the sender's one, e.g. smtp.a.org, and the recipient's one, e.g. mx.b.org). The first MTA assigns the ENVID (see later), while the last one passes the message to the MDA.
- at every MTA hop, the machine adds a **Received** field inside the header. However this field, like many others, is not protected, so a third party can fake or modify it.

**Mail Delivery Agent (MDA)** receives the message from the last MTA, can apply rules and filters, and then stores it inside the recipient's local **mailbox** (message store).


### Message recipient
**Message Store (MS)** is just the place where messages are stored, and where the user can read or delete them.

**MUA (recipient side)** lets the recipient get the messages using:
- **POP3**, to download the mail and read it offline
- **IMAP4**, to read the mail online (messages stay on the server)
- (or proprietary protocols, e.g. Microsoft Exchange)

Note: MUAs use SMTP only to **send** messages, never to read them.


## SMTP
The message forwarding between the parts of the e-mail system seen before is ruled by the **SMTP** protocol (RFC 821, updated by RFC 5321). An SMTP message is made of two logically separated parts that travel together: **[envelope, {header, body}]**.<br>
The **envelope** contains the delivery parameters (the SMTP commands MAIL FROM and RCPT TO) and is used by the servers to understand where the message must be delivered. It is first given by the sender's MUA, it can be rewritten along the way, and it is removed by the MDA at delivery.<br>
EX:
```
MAIL FROM:<john@doe.com>          ← envelope
RCPT TO:<boss@workplace.com>      ← envelope
DATA
From: "John Doe" <john@doe.com>   ← header
To: Boss Workplace <boss@...>     ← header
Subject: Sick note                ← header

Hello boss, ...                   ← body
```
- the part before the @ sign is the **local part** of the address
- the part after the @ sign is a **fully qualified domain name** (very important for the MTAs)

**Important:** the envelope and the header are independent. The `To:` field in the header is not necessarily where the message is delivered (the real list is in RCPT TO), and the `From:` field does not have to be the real sender. This is the base of many attacks (spoofing).

### Header and body
These two parts are defined by the **Internet Message Format (IMF, RFC 5322)** and are separated by a blank line.<br>
The header is a set of fields in the form `Field: value`. If a value is longer than one line, it continues on the next lines, which start with a space or a tab. Each line must be at most 76 characters long.<br>
**Field names and values are restricted to 7-bit ASCII characters** (normal letters, numbers 0-9 and punctuation). Non-ASCII values can be written using MIME *encoded words*.<br>
The body is the content of the message, as unstructured text.

**Mandatory header fields**:
- From - Sender's email address.
- To - Email recipients. Multiple email addresses can be included.
- Date - The date and time when the message was sent. It follows a specific format (RFC 5322).
- Message-ID
- Subject - A brief summary of the content of the email.

**Most important optional fields**
- Cc / Bcc - additional recipients (in Bcc they are hidden).
- Reply-To - address where replies should be sent, if different from From.
- In-Reply-To - contains the Message-ID of the email to which this message is a response. It is used for threading in email clients.
- References - list of the Message-IDs of the previous emails in the thread.
- Sender - used when the person sending the email is different from the one in From.
- Return-Path - address that receives the bounce-back messages if the email cannot be delivered.
- Received - added by each mail server that processes the message, tracking the route of the email. Each hop adds a new "Received" field.

### Message IDs
Each message is identified through two kinds of IDs:
- **Message-ID**:
    - assigned by the MUA or the MSA
    - it's inside the header, so it is also visible to mail clients
    - associated to the message content and globally unique
    - its format is similar to that of a mailbox, with two parts separated by @
        - the right side specifies the domain or host that assigns the identifier
        - the left side contains an opaque string that uniquely identifies the message within the domain on the right side
    - used for threading, to find duplicates, and for DSN (Delivery Status Notification) tracking

EX: Message-ID: *<20241001102233.12345@example.com>*

- **ENVID** (envelope identifier):
    - it's inside the **envelope**, so it is removed by the MDA
    - assigned by the first MTA; its content is opaque
    - used for message tracking (DSN) of a **single** posting/delivery: it is useful for the first MTA to know the status of the message
    - every MTA that supports DSN must pass the ENVID to the next hop and put it inside the delivery notifications it generates
    - an ENVID is used for one posting until the message is delivered: if the message is **re-posted** (e.g. forwarded again by an MTA), a new ENVID is used

# ESMTP
It is an extension of the SMTP protocol (RFC 5321) and it is backward-compatible with it: a client that uses plain SMTP is still served.<br>
In ESMTP the client says hello to the server with the **EHLO** command (in SMTP it was **HELO**). The server answers with the **list of extensions it supports**, so the client knows which ones it can use.<br>
Main commands/extensions:
- **STARTTLS**: in SMTP all the text of the message travels in clear; with this command the connection is switched to an **encrypted (TLS) connection**
- **AUTH**: the client must authenticate to the server before sending, so only authorized users can send mail through it (this helps against spam)
- **8BITMIME**: allows 8-bit data transmission (plain SMTP only allows 7-bit ASCII)
- **SIZE**: the client declares the size of the message, so the server can refuse it if it is too big
- **CHUNKING**: the message can be sent in chunks
- **DSN**: Delivery Status Notification
- **SMTPUTF8**: allows UTF-8 in mailbox names and header fields

# MIME (MULTIPURPOSE INTERNET MAIL EXTENSIONS)
MIME is an official Internet standard that specifies how messages must be formatted so that they can be exchanged between different email systems.
It allows the inclusion of virtually any type of file or document in an email message (text, images, audio, video, documents...).

Main features:
- Support of character sets other than ASCII
- Content type labeling system
- Support of non-text content in e-mail messages
- Support for compound documents (bodies with multiple parts)

The most important one is the support of non-ASCII character sets.

So, in general, MIME converts the data of messages that don't contain only simple ASCII text, because the e-mail system can only carry **7-bit NVT ASCII** .<br>
In the architecture it sits on the user agent side(MUAs): on the sender side it **encodes** the non-ASCII content before it enters the e-mail system; on the recipient side it **decodes** it back to its original form.

Every content inside the message is mapped, through its extension, to a **MIME type** made of a primary type and a subtype separated by a / (as text/html)
- EX. .txt → text/plain, .jpg → image/jpeg, .zip → application/zip

## MIME Encoding
![alt text](image-4.png)
The **Content-Transfer-Encoding** header says how the content was encoded: 7bit, 8bit, binary, base64, quoted-printable.
- non-textual content is encoded in ASCII for the transmission and decoded back to its original form when it is received.

### Base64
It is a binary-to-text encoding that uses only 64 characters: A-Z, a-z, 0-9, +, /
1. take 3 bytes of data (24 bits)
2. split them into 4 groups of 6 bits
3. compute the number of each group (a value from 0 to 63, EX. 000111 → 7)
4. use the number as an index in the table *ABC...XYZabc...xyz0123456789+/* to get the ASCII character (EX. 7 → H)
5. so 3 bytes become 4 ASCII characters; at the end, zero, one or two `=` are used as padding if the data are not a multiple of 3 bytes

Note: base64 makes the data about 33% bigger (3 bytes → 4 characters).

### Quoted-printable
It is used for text that is **mostly ASCII** but also contains some non-ASCII bytes (e.g. accented letters). It is a mixed approach, and the result is still readable by a human.
- **ASCII printable characters** (codes from 33 to 126) are kept as they are, **except** the `=` sign (code 61)
- **any other byte** (non-ASCII, or the `=` itself) is encoded with 3 characters: an `=` followed by two hexadecimal digits (0–9, A–F) that represent the value of the byte
    - EX. `=` → `=3D`
    - EX. "é" in UTF-8 is the 2 bytes C3 A9 → `=C3=A9`, so "Café" → `Caf=C3=A9`
- **special cases for SPACE and TAB**: they can stay as they are inside a line, but at the end of a line they must be encoded (`=20` for space, `=09` for tab), because some systems delete spaces at the end of lines
- lines can be at most 76 characters long: a longer line is split with a **soft line break**, an `=` at the end of the line, which is removed during decoding

**Base64 vs quoted-printable**: quoted-printable is better for text with few non-ASCII characters (small and readable); base64 is better for binary data like images or attachments (with quoted-printable almost every byte would become 3 characters).

## Multipart subtypes
A message with a `multipart` Content-Type contains **several parts**, and each part has its own headers (Content-Type, Content-Transfer-Encoding...) and its own body.<br>
The parts are separated by a **boundary** string, defined as a parameter of the Content-Type:
- each part starts with `--` + boundary
- the end of the last part is marked by `--` + boundary + `--`

Main subtypes:
- **mixed** - the parts have different Content-Types (EX. body text + attachment); their order matters
- **parallel** - like mixed, but the order of the parts does not matter
- **digest** - to send multiple text messages together; similar to mixed, but the default type of each part is `message/rfc822`
- **alternative** - each part is a different version of the same content (EX. text/plain + text/html); the client shows the best version it can display
- **message** type (not multipart, but used together with it): `message/rfc822` contains a whole e-mail message with its headers (EX. a forwarded mail)

EX. body + attachment:
```
From: Some One <someone@example.com>
MIME-Version: 1.0
Content-Type: multipart/mixed;
        boundary="XXXXboundary text"

This is a multipart message in MIME format.

--XXXXboundary text
Content-Type: text/plain

this is the body text

--XXXXboundary text
Content-Type: text/plain;
Content-Disposition: attachment;
        filename="test.txt"

this is the attachment text

--XXXXboundary text--
```
- **Content-Disposition: attachment** tells the client to show that part as an attachment with the given file name.

Multipart parts can be **nested**: a common structure is a `multipart/mixed` that contains a `multipart/alternative` (text + HTML version of the body) and then the attachments (usually in base64).
```
multipart/mixed
├── multipart/alternative
│   ├── text/plain   (quoted-printable)
│   └── text/html    (quoted-printable)
└── text/plain attachment (base64)
```
Note: HTML messages often include a plain text copy too (with multipart/alternative). HTML allows links and images in the body, but makes the e-mail bigger.
